# Soloco 飞书反馈表单契约

提交前始终运行 `base +form-detail`；实时 `questions[]` 优先于本文。本文最后核对时间：2026-08-01。

## 目标

首次使用前，将下表占位值替换为你有权使用的飞书多维表格和表单信息。不要把公司内部地址或访问凭据提交到公开仓库。

| 项目 | 值 |
|---|---|
| 表单名称 | `产品体验与 Bug 反馈` |
| 表单说明 | `用得别扭、点不动、看不懂，都算问题，欢迎提交。一次只提交一个问题；同一个问题请不要重复提交。Bug 请务必附上复现步骤和截图/录屏——没有这两样我们基本无法定位。` |
| 收集页 | `<FEISHU_COLLECTION_URL>` |
| 表单分享页 | `<FEISHU_FORM_SHARE_URL>` |
| share token | `<FEISHU_SHARE_TOKEN>` |
| Base token | `<FEISHU_BASE_TOKEN>` |
| table ID | `<FEISHU_TABLE_ID>` |

## 实时字段顺序

| # | 字段 | 必填 | 类型 | 合法值 / 填写规则 |
|---:|---|---:|---|---|
| 1 | 你的姓名 | 是 | text | 使用已验证的飞书用户名；无法获取时询问用户 |
| 2 | 标题 | 是 | text | 一句话描述一个问题，建议 15–60 字 |
| 3 | 问题类型 | 是 | select | `Bug`、`体验问题`、`产品建议` |
| 4 | 所属模块 | 是 | select | `目标与使命`、`运行与任务`、`组织画布`、`通知与收件箱`、`设置与账号`、`客户端安装/更新`、`官网与营销页`、`其他` |
| 5 | 严重程度 | 是 | select | `阻断（完全无法继续）`、`严重（主流程受影响）`、`一般（有绕过办法）`、`轻微（观感/文案）` |
| 6 | 问题描述（是什么） | 是 | text | 通俗说明、预期、实际、证据、可能原因 |
| 7 | 复现步骤 | 否 | text | 只写证据支持的步骤；`Bug` 按表单说明必须提供 |
| 8 | 截图 / 录屏 | 否 | attachment | 草稿展示文件名、类型、大小；`Bug` 按表单说明必须提供 |
| 9 | 环境 / 版本 | 否 | text | 系统、客户端、运行时、诊断包名和完整 SHA-256 |
| 10 | 解决建议（怎么解决） | 否 | text | 用“建议”表述，不冒充已验证修复 |
| 11 | 设计建议（怎么设计） | 否 | text | 仅交互或信息架构问题填写 |

分类规则：执行、等待、恢复和任务状态问题归 `运行与任务`；登录权限归 `设置与账号`；安装启动归 `客户端安装/更新`；证据不足或跨模块归 `其他`。严重程度按用户影响选择，不按日志中的错误数量选择。

## 用户确认草稿

必须按实时题目原顺序逐字段展示，不得把多个字段合并成一行。单选、多选和其他枚举题在该行列出 `options[]` 的全部合法值；文本和附件题写 `—`。选择值不属于实时选项时写“无效（请从可选项中选择）”，并暂停确认与提交。选填项没有内容时写“未提供”；附件没有上传时写“本次不上传”。`Bug` 缺少复现步骤或截图/录屏时写“缺失（提交前必须补充）”，并暂停提交。

## 提交 Payload

确认草稿与 payload 必须逐字段一致。普通字段放在 `fields`；附件只放在顶层 `attachments`，不要把附件行写进 `fields`。

```json
{
  "fields": {
    "你的姓名": "周超",
    "标题": "任务已暂停但界面仍显示运行中",
    "问题类型": "Bug",
    "所属模块": "运行与任务",
    "严重程度": "严重（主流程受影响）",
    "问题描述（是什么）": "通俗说明：……\n预期：……\n实际：……\n证据：……\n可能原因：……",
    "复现步骤": "1. ……\n2. ……",
    "环境 / 版本": "……\n诊断包：example.txt；SHA-256：<full sha256>",
    "解决建议（怎么解决）": "建议：……",
    "设计建议（怎么设计）": ""
  },
  "attachments": {
    "截图 / 录屏": ["./running-state.png"]
  }
}
```

提交成功要求退出码为 0 且顶层 `ok: true`；随后用诊断包 SHA-256 回查记录。
